Builds on B9.2 + B9.2.1 without changing the deployed Player, streaming logic, or OX Worker.

## Apply ONLY to C:\Users\dundi\OX-Novels-B9.2-TEST

1. Keep the original `C:\Users\dundi\OX-Novels` unchanged.
2. Back up the `OX-Novels-B9.2-TEST` folder.
3. Unzip this patch into the TEST folder, preserving paths.
4. Run `local-player-b9.2\B9.2.2-VERIFY-LOCAL.bat`.
5. Send the results to the chat. Do not deploy.

This package adds a D1 **staging schema file**, not an applied migration. Nothing creates a Cloudflare database, runs Wrangler, changes `.dev.vars`/`.dev.vars.live-backup`, touches the main OX production D1, or accesses real Google Drive.

## What is tested

- Durable resumable per-story jobs using SQL tables shaped for a private D1 database.
- Paginated Drive folder recording (max 40 tracks and 25 child folders per step).
- Each page committed with a transactional D1-style batch; an incomplete page never completes a folder.
- Reject missing, truncated, changed, out-of-order, duplicate and invalid inputs without activating a new catalog.
- Sealing requires every folder and page complete, and at least one track.
- Encrypts no more than 12 track tokens in one step with the existing AES-GCM t1 format.
- Recovery after closing/reopening local SQLite database in the middle of a job.
- Real 2,848-track sample workload; status is explicitly `READY_LOCAL`, **not activated**.

## Remaining blockers, not hidden by test success

1. Not integrated into `processScanQueue`, `Cron`, or live Drive resolver. Existing B9.2 scanner still does whole-story work per Worker invocation; it remains DISABLED.
2. Apps Script resolver needs a **verifiable paginated protocol** with totalPages/complete/truncated. This test uses local source data to simulate pages. Do NOT pretend current resolver supports page tokens.
3. KV assembly/publication of the final complete encrypted catalog is not implemented. Atomic activation, deletion/tombstones, and public playback are unchanged from B9.2 baseline.
4. IMPORTANT: staging ALL 242 stories into D1 each night is not viable on Free. There are 154,699 tracks, already above 100,000 daily D1 written rows. The production scanner needs a metadata/fingerprint-only preflight, then D1 stage ONLY the ~5-20 changed stories. This is not built yet.
5. Queue jobs, 10 ms Free Worker CPU, D1 reads/writes and recovery under concurrent retries need real isolated staging measurement before any Cloudflare rollout.
6. Each D1 stage has raw Drive file IDs privately in the staging database. Never expose D1 or its rows via public frontend. Design deletion/retention before production use.
7. This adds *no* automatic midnight scanning functionality yet. Full 242-story scan runs remain a goal, not a delivered feature.
8. Free Queues retention is only 24 hours; design must be able to resume from D1 without relying on retained messages.

Resource planning: Cloudflare current Free-tier limits: Workers CPU 10 ms/invocation, Queues 10,000 operations/day, KV 1,000 writes/day, D1 100,000 rows written/day and 5 million rows read/day. Limits are account-wide; batch operations and retries count. These tests do not measure Cloudflare CPU. Always abort before quota and keep previous catalog.

The schema is a **local prototype only**: `local-player-b9.2/migrations/0001_b922_staging_only.sql`. Do not apply it to any remote D1 database yet.
