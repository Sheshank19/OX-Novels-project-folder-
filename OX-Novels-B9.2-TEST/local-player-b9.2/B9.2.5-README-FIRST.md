## What this patch adds

- `b925-resolver-protocol.js`: a strict **local-only** begin/page/end API contract requiring a pinned snapshot revision, complete paginated responses, exact folder/page/revision binding, and a final consistency proof. It also includes an injected **fake resolver** built from existing local cached catalogs. This is not a Google Apps Script implementation.
- `b925-durable-scheduler.js`: a **local D1-style/SQLite test** of one-page-at-a-time work with database-persisted progress, lease/epoch fencing for claims/ACKs, restart recovery, exponential-backoff retry to **15 failed attempts**, preservation of previous catalog, and explicit separate changed-story full staging.
- `0003_b925_SCHEDULER_LOCAL_ONLY.sql`: **offline-only** schema supplementing `0002_b924_METADATA_TEST_ONLY.sql`. NOT for live/production use.
- `b925.test.mjs`: **19 new local tests** for lease contention/expiry, restart recovery, incomplete/expired snapshots, 2,848-track story, changed folder/track detection, retry exhaustion, quota estimate and safe nonpublication.

## Explicit blockers before any cloud staging

1. **Real Apps Script source missing**. The current uploaded project has a client calling `mode:list_children`, but the **server-side Google Apps Script resolver implementation is not in the ZIP**. No live pagination, snapshot creation, stable ordering or end-to-end revalidation has been implemented. A resolver returning the same string multiple times is **not evidence** that Google Drive stayed unchanged. Pinned snapshots might require a different design or revalidation if Apps Script cannot provide them.
2. **No cloud dispatcher**. One Queue message per story is only a theoretical low-operations estimate; the code does not actually schedule thousands of Worker invocations or handle Cloudflare Cron across Pacific daylight-saving transitions.
3. **Lease-to-commit race still needs true database fencing**. The local scheduler validates a lease before it calls the existing B9.2.4 page commit, but the page commit and the scheduler lease check are NOT one atomic D1 transaction. A revoked/expired Worker may still race with a current claimant in a real distributed runtime. The offline stale ACK/claim tests do not prove distributed fencing safety. Do not hook it to live endpoints.
4. **No verified Free CPU feasibility**. Cloudflare Workers Free has 10ms CPU/request, 50 subrequests/invocation and 100k requests/day. The local tests cannot measure Worker CPU consumption.
5. **No account-wide quota verification**. Estimates assume Queue operations (3 per story message) and count a *lower bound* for D1 writes. They omit SQLite row writes for folder inserts/updates, query read costs, retries, concurrent users/audio streaming, and other workloads. The planner explicitly says **productionApproved:false**.
6. **No KV publication or production connection**. Changed stories remain `NEEDS_FULL_STAGE` after complete comparison; catalog rebuild/atomic activation and admin notifications are still future work. Current original static catalogs and B6.5 streaming code are untouched.
7. **Snapshot expiry handling needs production design**. The mock can deliberately expire a snapshot and preserve the previous catalog, but real long-running complete-library scans require a trustworthy Drive snapshot/restart mechanism.
