## What this version demonstrates

- 242/242 original hashed fingerprints match the user-supplied local source metadata and are classified unchanged, **without staging track rows**.
- It notices new episodes in existing folders, added folders, renamed/deleted episodes, replaced source versions, and new stories.
- Incomplete, truncated, skipped, conflicting or malformed resolver pages cannot be called unchanged; duplicates and folder cycles fail closed.
- **Two already-published original catalog baselines contain 0 tracks:** `strongest-replication` and `twice-upon-a-time`. They are allowed to remain *unchanged*, while a new/modified empty catalog is rejected. This is only a local source observation, NOT evidence of a newly broken production story.
- Full real-source baseline: 242 stories; 1,923 folders; 154,699 tracks; 4,978 **simulated** metadata pages at 40 tracks/25 folders per page.
- One Queue message **per metadata page** at ~3 operations/message would use **14,934 Queue operations**, already exceeding Free's 10,000/day allowance before retries. Therefore this approach is **blocked**. Grouping per story reduces Queue operations but does not solve Free CPU/subrequest limits without tests.
- A conservative changed-only staging planner counts estimated D1 writes and Queue operations and denies approval when the complete story set/account-wide quota usage is unknown.

## Not delivered yet (blockers)

1. The current Google Apps Script resolver has **not** been modified. Tests simulate paginated metadata using the 242 local cache files. Do NOT assume a real `pageNo`/`totalPages` protocol currently exists.
2. The preflight helper holds one story's metadata in memory; it does **not** have durable metadata-only checkpoints across Worker invocations. It is not wired into B9.2 `processScanQueue` or scheduled Cron. Cloudflare Workers Free has a 10 ms CPU limit per invocation, still unverified.
3. The preflight planner does **not** measure real account-wide D1/Queue usage and cannot authorize production.
4. Changed-story D1 staging and atomic KV publish remain separate/incomplete.
5. Source changes during a multi-page scan can still occur; the eventual resolver protocol will need a robust revision/snapshot or consistency verification, not just page counts.
6. No automatic daily scan, admin remote updating, or live Cloudflare staging has been enabled by this patch.

## Quota references checked October 10, 2026

- Workers Free: 10 ms CPU / invocation, 50 external subrequests / invocation: https://developers.cloudflare.com/workers/platform/limits/
- Queues Free: 10,000 operations/day, reads/writes/deletes each count: https://developers.cloudflare.com/queues/platform/pricing/
- D1 Free: 100,000 written rows/day, 5 million read rows/day: https://developers.cloudflare.com/d1/platform/pricing/

**Safety rule:** If scanning is incomplete, over quota, or fails, keep existing published catalogs. Never enable the B9 scanner or deploy either Worker from this ZIP.
