# OX Audio Player — B9.2.1 local development patch

**Status: LOCAL ONLY, NOT PRODUCTION-READY.** This is an incremental overlay on B9.2 in the separately created `OX-Novels-B9.2-TEST` project. It does **not** create resources, set secrets, modify either `.dev.vars` file, touch R2, make a network request, or deploy either Cloudflare Worker.

## What this update completes

- Local prototype for **one-Drive-folder-at-a-time** scan checkpoints, validated using a real cached **2,848-track / 30-folder** story. The prototype works with an *in-memory cursor in local tests*, and is **not yet connected to Cloudflare D1/Queue**.
- Token-encryption prototype for **1–12 tracks per step**. It preserves the existing AES-GCM `t1` token format. This is **not yet connected to a durable cloud staging store or live catalog publishing**.
- Change and failure event history for the B9.2 Admin (archives only actionable new/updated/failed events, not every unchanged story) and a more honest **latest-cycle summary** showing `processed`, `pending`, `unchanged`, `updated`, `new`, and `failed`.
- Added **Retry Failed**, **Change History** and changed-story summaries to the existing B9.2 Player Admin. The Admin still requires its pre-existing authenticated session; no new public admin routes.
- Fail-closed resolver input checking: truncated, missing, malformed file/folder IDs and invalid track sizes cannot silently produce partial new catalogs.
- A failed **new** story is shown in Admin even without a previous static/active catalog.

## IMPORTANT: still BLOCKED for production

The B9.2 Worker currently still calls the original single-invocation `scanSource` and `safeCatalog`. B9.2.1's chunked helpers are **isolated prototypes**, not yet integrated into `processScanQueue`; attempting to process a 2,848-track story with that existing handler may exceed the Workers Free CPU limit. **Keep `B9_SCANNER_ENABLED=false`, and do not run configuration/deployment BAT files.**

Before enabling remote scanning, we must design, implement and test:

1. A durable **D1-based checkpoint layer in Player Account B** (or a verified alternative) so each Queue message can continue the exact same story safely after restarts, out-of-order delivery or retries, without using thousands of daily KV writes. D1 Free currently has 5 million rows read/day, 100,000 rows written/day, and a 500 MB per-database / 5 GB per-account storage envelope. We have **not** created a database or modified account configuration.
2. A bounded final catalog assembly/publish stage, with track-neighbor links and verified atomic promotion. Until this is finished, the chunked tokens cannot become a live catalog.
3. Measure actual Cloudflare **Free Worker 10 ms CPU** usage across all stages with staging Workers (Node benchmarks are not a substitute), including large stories, queue re-delivery, and fail-safe behavior.
4. Enforce a daily Queue capacity budget that includes all retries, even when twenty or more large stories change on the same day. The existing B9.2 `DAILY_QUEUE_CAP` only limits **initial story jobs**, not all chained messages/retries.
5. Validate complete daily/nightly archival and notification delivery, Free KV eventual consistency, and atomic rollback on failures.
6. Stage on **separate** test bindings without touching the currently working Player Worker and without deploying the main `oxnovels.top` Worker.

## Why Queue budget matters

Current catalog manifest: **242 stories**, **1,923 folder nodes**, **154,699 tracks**. A future naive per-folder staged scan plus per-story start/finalize would require at least **2,407 Queue messages**, or approximately **7,221 Queue operations** at 3 operations/message, even before changed-track token jobs, 15-attempt retry overhead, duplicate deliveries and oversized queue payloads. Cloudflare Queues Free offers **10,000 operations per day**. This is a feasibility estimate only, not a verified working architecture. The local planner flags scenarios over a *conservative* 8,500-op envelope; it is not an enforcement mechanism.

## Install safely on Windows

1. KEEP your original `C:\Users\dundi\OX-Novels` untouched.
2. KEEP the existing separate `C:\Users\dundi\OX-Novels-B9.2-TEST` folder that passed the original 9 tests. Make a backup of it if convenient.
3. Extract this ZIP **only** into `OX-Novels-B9.2-TEST`, preserving file paths. Replace only same-named included development files.
4. Run `local-player-b9.2\B9.2.1-VERIFY-LOCAL.bat` in the **TEST** folder. Expect **20 mock tests** passing on the supplied B9.2 source, with a harmless optional Node module-type warning and one deliberate simulated failure log.
5. Send the final `pass/fail` lines. **Do not** run `CONFIGURE-B9.2-FREE.bat`, enable `B9_SCANNER_ENABLED`, or deploy either Cloudflare Worker.

## Why the ZIP does not include the full project

This ZIP is a small overlay, not the complete OX repository. It includes neither secrets nor existing catalog static assets, databases, site build outputs, `node_modules`, or original Cloudflare account configuration. The existing streaming, protected handoff, emergency Player ON/OFF switch, MP3 and large M4B source files remain unchanged.
